# 研发费用合规智能管理系统 后端接口联调文档

## 1. 文档目的

本文档用于统一当前 Spring Boot 后端与 React 前端的接口规范、字段约定、自测方式与第一阶段后端改造目标。

当前开发策略：

- 先完成后端接口、权限、数据结构与文件上传能力
- 前端后续严格按本接口文档接入
- 联调放在后端主要能力稳定后集中处理

---

## 2. 已确认的业务边界

### 2.1 账号体系与员工体系完全分离

系统内存在两套完全不同的数据概念，后端开发时必须严格区分：

- `sys_user`
  - 含义：后台登录账号
  - 特点：数量少，用于登录、权限控制、操作审计
- `employee`
  - 含义：公司业务员工
  - 特点：数量多，用于项目参与人员、研发费用归集、月度成本统计

禁止出现以下错误理解：

- 不是所有公司员工都有后台登录账号
- `employee` 和 `sys_user` 不一一对应
- 员工姓名不能直接替代后台账号身份

### 2.2 角色定义

当前角色以以下三个为准：

- `admin`
  - 平台管理员
  - 不属于任何公司
  - 只负责公司管理
  - 后续使用单独前端界面

- `branch_admin`
  - 公司管理员
  - 属于某一个公司
  - 业务权限与普通用户相同
  - 额外拥有“可修改已结算项目/月度记录”的权限
  - 可管理本公司后台账号

- `user`
  - 普通后台用户
  - 属于某一个公司
  - 执行业务录入、查询、提交待结算
  - 只能修改自己的资料与密码

### 2.3 多公司规则

- `admin` 不受 `company_id` 业务数据隔离限制
- `branch_admin` 与 `user` 必须受 `company_id` 隔离
- 所有公司业务数据查询、详情、更新、删除都必须校验公司归属
- 除 `admin` 外，任何角色都不能读写其他公司的业务数据

### 2.4 当前前端界面范围

当前 React 前端优先服务以下角色：

- `branch_admin`
- `user`

`admin` 后续使用单独界面，但共用同一套后端账号体系与认证能力。

## 3. 统一接口规范

## 3.1 Base URL

统一使用：

```text
/api/v1
```

认证接口保留：

```text
/api/auth
```

### 3.2 请求头规范

除登录接口外，所有接口默认需要以下请求头：

```http
Authorization: Bearer <token>
Content-Type: application/json
```

文件上传接口使用：

```http
Authorization: Bearer <token>
Content-Type: multipart/form-data
```

### 3.3 统一返回格式

后端统一返回如下结构：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

分页接口统一返回：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "list": [],
    "page": 1,
    "size": 10,
    "total": 0
  }
}
```

### 3.4 统一错误返回格式

```json
{
  "code": 400,
  "message": "参数错误",
  "data": null
}
```

推荐错误码：

- `200`：成功
- `400`：参数错误
- `401`：未登录或 token 无效
- `403`：无权限
- `404`：资源不存在
- `409`：业务冲突，例如重复创建、状态不允许
- `500`：系统异常

### 3.5 分页参数规范

列表接口统一使用以下参数：

- `page`：页码，从 `1` 开始
- `size`：每页大小

示例：

```text
GET /api/v1/projects?page=1&size=10
```

### 3.6 日期与时间规范

- 日期：`yyyy-MM-dd`
- 月份：`yyyy-MM`
- 日期时间：`yyyy-MM-dd HH:mm:ss`
- 金额类型：统一返回 `number`

### 3.7 枚举值规范

项目状态：

- `ongoing`
- `ended`

月度记录状态：

- `draft`
- `pending_settlement`
- `settled`

账号状态：

- `enabled`
- `disabled`

## 4. 文件上传规范

### 4.1 上传目录配置

必须通过配置文件读取，不允许写死本地开发路径。

推荐配置：

```yaml
app:
  upload:
    base-dir: ${APP_UPLOAD_BASE_DIR:./uploads}
```

说明：

- 本地开发可使用默认 `./uploads`
- 测试环境和生产环境使用环境变量覆盖
- Docker 部署时将该目录挂载到宿主机

### 4.2 目录结构

第一阶段建议目录结构：

```text
uploads/
  company-{companyId}/
    project-{projectId}/
      {yyyy-MM}/
        labor/
        direct/
        deprec/
        intangible/
        design/
        equip/
        outsource/
        other/
```

示例：

```text
uploads/company-1/project-2/2026-03/labor/
```

### 4.3 文件命名规则

建议文件名：

```text
{projectId}_{yearMonth}_{category}_{timestamp}_{originalFilename}
```

示例：

```text
2_2026-03_labor_20260402153000_invoice.pdf
```

### 4.4 费用分类编码

后端需统一向前端对齐以下 8 类费用分类：

- `labor`
- `direct`
- `deprec`
- `intangible`
- `design`
- `equip`
- `outsource`
- `other`

说明：

- 后端现有旧分类和旧 JSON 结构需要调整
- `JsonUtils` 与月度数据解析逻辑必须同步修改

## 5.1 认证接口

### 5.1.1 登录

```http
POST /api/auth/login
```

请求体：

```json
{
  "username": "branch_admin_bj",
  "password": "123456"
}
```

成功返回：

```json
{
  "code": 200,
  "message": "登录成功",
  "data": {
    "token": "Bearer xxxxxxxxx",
    "user": {
      "id": 2,
      "username": "branch_admin_bj",

      "role": "branch_admin",
      "status": "enabled",
      "companyId": 1,
      "companyName": "北京分公司"

}
```

```json
{
  "code": 401,

  "data": null
```

```bash
curl -X POST "http://localhost:8080/api/auth/login" ^
  -H "Content-Type: application/json" ^
```
